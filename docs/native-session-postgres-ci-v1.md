Unknown profiles fail.

## Safety contract and execution order

1. Require the explicit `github-service-v1` profile, GitHub Actions hosted Linux/X64 context, exact repository/name ID (`1247983326`), `verify` job and `Backend CI` workflow. Accept only existing `push` on main or PR merge-ref events. Require well-formed run/attempt/SHA, and compare checked-out HEAD with `GITHUB_SHA`. Reject ambient PG variables, database URLs, Docker overrides and `NODE_OPTIONS`.
2. Before any database connection, inspect only projected metadata using `/usr/bin/docker --host unix:///var/run/docker.sock`. Require the service ID from this job, a different original-service ID, exact digest/image architecture/entrypoint/command, healthy running state with no restart/OOM, matching run/repository/attempt/SHA labels, no privilege escalation, no custom devices/capabilities and no restart policy. No environment values, health logs or database contents are inspected.
3. Check both requested and effective `5432/tcp` publication: exactly one `127.0.0.1:55432` binding. Require the exact job bridge network, network ID, matching endpoint IDs/IPs, IPv4 subnet and gateway, with distinct native/original-service endpoints. Reject extra networks, extra port mappings and host networking. Reject bind mounts, volume inheritance, named/anonymous volumes, extra mounts or missing/changed tmpfs configuration. Docker may omit legacy `--tmpfs` entries from `Mounts`; if reported, only the exact tmpfs is allowed, while `HostConfig.Tmpfs` is always required.
4. Connect only to literal host `127.0.0.1`, port 55432, bootstrap database `postgres` using the synthetic bootstrap role. PostgreSQL must report the exact inspected **container** IP and port 5432, and client IP equal to the inspected bridge gateway with a valid client port. Require numeric finite integer version `160015`, no recovery, expected user/database and no bootstrap marker. No broad private-address allowance exists. SQL address mismatches fail; they are not repaired or silently generalized.
5. Require empty bootstrap user namespaces and only `postgres`, `template0`, `template1`; reject any existing fixture role. Create a new random database and nonsuperuser fixture role without `IF EXISTS`, reset, reuse or drop logic. Each DDL acknowledgement must match. Set its exact disposable database comment. Collision, partial creation or ambiguous acknowledgement aborts; the failed job's service is discarded by GitHub rather than retried or repaired by SQL.
6. Close the bootstrap pool. Run the accepted preparation script as the fixture role, then the accepted native integration file, strictly serially. Preparation still verifies emptiness on its leased transaction before DDL, uses the accepted transaction-local public creation path, applies only identity migration 002 and candidate SQL, and verifies the transaction/commit acknowledgement. CI empty-target checks additionally reject user types and unexpected namespaces.
7. Preparation, the suite and every recovery worker import the same profile selector. Each process independently repeats service inspection before connection, then rechecks service identity and SQL database identity before proceeding. Their frozen target/connection configuration and registered identity cannot be changed after validation. Recovery workers inherit the identical explicit designation and run context.
8. The structured Node reporter requires the accepted **16-test manifest**, all passed, with zero failed/skipped/TODO/cancelled tests and a successful final summary. Missing prerequisites, missing summary, skipped cases, child failure or timeout fails `verify`. Arbitrary child stdout cannot impersonate the summary. No filtered subset, automatic retry or `continue-on-error` is used. The reporter emits counts only, not fixture records or arbitrary child diagnostic payloads.

These checks establish a conservative environment contract inside a reviewed hosted workflow. They do not cryptographically attest GitHub, the Docker daemon, the runner or arbitrary PR code. Both services share the job's ephemeral bridge; this is database/process separation, not adversarial network isolation or egress prevention. The workflow introduces no production secrets or credentials; synthetic passwords confer access only to that disposable fixture. No database dumps or diagnostic artifacts are uploaded.

## Runtime/resource assumptions and first hosted gate

- Existing verify timeout remains **15 minutes**. Prior feasibility evidence observed approximately 9m32s total and 8m05s for the original PostgreSQL stage. These are historical observations, not performance promises for this candidate.
- Budget an estimated **1–3 additional minutes** for native inspection, provisioning/preparation and 16 cases, plus image pull/startup variability. Each native child has a 180-second hard timeout; metadata commands each have a 5-second bound; existing pool/query timeouts remain. The outer job can expire sooner. The three-minute per-child bounds are limits, not evidence of a six-minute expected stage.
- [Standard public Linux runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) currently provide 4 vCPUs, 16 GB RAM and 14 GB storage. Expect a few hundred MiB for another lightly loaded PostgreSQL process plus fixture data, capped at 1 GiB of tmpfs; no container-wide memory cap is claimed. Provisioning uses one connection; accepted tests retain their 12-connection pool and bounded concurrency cases. Both servers run simultaneously, while their test suites run serially.
- [Tmpfs](https://docs.docker.com/engine/storage/tmpfs/) avoids persistent volume reuse but can use host swap. This fixture tests transactions and application-process recovery; it does **not** establish power-loss durability, PostgreSQL-server restart durability or disk behavior. No crash/restart of the service is introduced.
- Actual hosted verification must confirm image pull/digest representation, Docker format fields and tmpfs behavior, effective loopback publication, bridge gateway/client address relationship, fresh role/schema privileges, SQL acknowledgements, all native cases/recovery subprocesses, existing PostgreSQL regressions and final job duration. Any mismatch fails closed and requires diagnosis/review, not a broader address or environment allowance.
- If the complete job approaches/exceeds 15 minutes, report measurements and seek a separately reviewed timeout/workflow adjustment. Do not skip old tests, split away the required result or silently widen this package.

## PR #15 diagnostics-only correction — November 8, 2026

The first hosted attempt on `f705c0b` passed 950 unit tests and 535 existing PostgreSQL tests, then failed in the native driver with its generic message. No native preparation or 16-case completion was established. Root cause remains **unresolved**; exception suppression was confirmed. This correction adds diagnostic visibility only and does not claim to fix the hosted failure. No hosted retry or remote operation is part of this correction.

The finite code vocabulary is defined in `tests/helpers/nativePostgresDiagnostics.ts`. Codes identify the executing boundary, not an inferred PostgreSQL/product root cause:

| Coverage category                      | Representative static codes                                                                                                                     |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Runner context / target designation    | `CONTEXT_REJECTED`, `TARGET_REJECTED`                                                                                                           |
| Docker collection / command / parsing  | `DOCKER_CONTAINER_READ_FAILED`, `DOCKER_CONTAINER_PARSE_FAILED`, corresponding image/network codes, `CHECKOUT_READ_FAILED`                      |
| Service identity and safety validation | `METADATA_REJECTED`, `SERVICE_RECHECK_FAILED`                                                                                                   |
| Bootstrap / SQL preparation            | `BOOTSTRAP_IDENTITY_FAILED`, `BOOTSTRAP_DATABASE_CREATE_FAILED`, `PREPARE_SCHEMA_FAILED`, `PREPARE_COMMIT_FAILED`                               |
| Child execution / timeout / report     | `PREPARATION_CHILD_FAILED`, `INTEGRATION_CHILD_FAILED`, phase-specific `REPORT_MISSING` / `REPORT_INVALID`, integration test/skip/summary codes |
| Cleanup                                | `BOOTSTRAP_CLEANUP_FAILED`, `PREPARE_ROLLBACK_FAILED`, `PREPARE_RELEASE_FAILED`, `PREPARE_POOL_CLOSE_FAILED`                                    |

Error properties, messages, stacks, causes and exception-supplied codes are never used to render these diagnostics. Internally created reports are tracked by object identity. Unknown exceptions use a static fallback. Cleanup executes once in the original order; a cleanup error is reported separately and cannot replace the original code. A cleanup-only failure still fails the command and prevents further preparation/integration. Preparation acknowledges success only after COMMIT acknowledgement, client disposal and pool cleanup have succeeded; a cleanup failure does not imply that an earlier commit was rolled back.

Example output for a primary failure followed by failed cleanup:

```text
NATIVE_PG_FAILURE BOOTSTRAP_DATABASE_CREATE_FAILED
NATIVE_PG_CLEANUP BOOTSTRAP_CLEANUP_FAILED
```

The parent captures and discards child stdout/stderr rather than forwarding or interpreting them. A dedicated fd 3 carries only allowlisted reports; the parent supplies the test-only `NATIVE_SESSION_CI_DIAGNOSTIC_FD=3` flag to those children. That flag grants no database authority and changes no persistent environment or workflow configuration. A forged diagnostic line embedded in exception text or ordinary output cannot influence the chosen code. The report parser accepts only finite codes and bounded records (4 KiB, at most one primary plus three cleanup lines). Nonzero exit, signal, spawn error or timeout always fails even if the child previously wrote a success report. Exit zero without the exact phase-specific success report also fails. Child capture is bounded at 1 MiB; overflow fails closed. This is an internal reporting channel for reviewed child code, not authentication of arbitrary malicious child programs.

Preparation success is `NATIVE_PG_STATUS PREPARATION_OK`. The reporter emits `NATIVE_PG_STATUS INTEGRATION_OK_16` only after consuming the complete unchanged 16-test manifest. The public driver emits its fixed final success message only after both children succeed. CLI outcomes remain exit 0 for success and exit 1 for failure. Metadata timeout (5 seconds), child timeout (180 seconds), job timeout (15 minutes), SQL/identity assertions, transaction checks and no-retry behavior are unchanged. Diagnostics cover entered orchestration paths; Node/loader failures before the program starts are outside this reporting channel.

Regression coverage independently exercises the six categories clarified by Matt/Nova, hostile exception strings/proxies, primary plus multiple cleanup failures, early rejection before I/O, missing/forged reports, child errors/signals/timeouts, and actual local Node reporter processes with 16, 15, skipped, TODO and failed synthetic cases. No real Docker command or PostgreSQL connection is used. The data-directory/WAL P3 and all native production-integration gates remain open.
